# 🔄 변경관리 및 UX/UI 개선 지침

본 지침은 청주도시공사 'Smart Operations Suite (SOS)' 통합 매뉴얼의 뼈대(구조), 디자인(UI), 사용자 경험(UX) 등을 수정하거나 보완할 때 지켜야 할 표준 프로세스입니다.

## 1. 목적
* 무분별한 코드 수정을 방지하고 시스템의 안정성을 확보하기 위함.
* SPA(Single Page Application) 구조의 특성(상태 유지, 뒤로가기 등)을 훼손하지 않기 위함.
* 시큐어 코딩 및 웹 접근성 지침을 지속적으로 유지하기 위함.

## 2. UI/UX 보완 시 준수 사항

### 2.1 SPA 상태 관리 및 라우팅 (History API)
* **뒤로가기 지원**: 페이지를 이동(DOM 전환)할 때는 반드시 `history.pushState`를 사용하여 브라우저 히스토리에 상태를 기록해야 합니다.
* **이벤트 리스너**: 사용자가 브라우저의 '뒤로가기/앞으로가기' 버튼을 눌렀을 때 엉뚱한 페이지로 이탈하지 않도록 `window.addEventListener('popstate', ...)`를 통해 DOM 상태를 동기화해야 합니다.
* **닫기/명시적 이동**: 모달, 팝업, 문서 뷰어 등 화면을 덮는 요소가 열릴 때는 반드시 우측 상단이나 접근하기 쉬운 위치에 명확한 `[닫기]` 버튼을 배치해야 합니다.

### 2.2 스타일링 (Tailwind CSS)
* 인라인 스타일(`style="..."`)의 사용을 엄격히 금지합니다.
* 다크/라이트 모드를 항상 고려해야 합니다. 특정 요소의 색상을 바꿀 때는 반드시 `dark:` 접두사를 포함한 다크모드 대응 색상도 함께 수정하십시오. (예: `bg-white dark:bg-gray-800`)

### 2.3 접근성 및 시맨틱 마크업
* 버튼 및 링크 추가 시 `aria-label`을 부여하여 스크린 리더기가 읽을 수 있게 하십시오.
* 아코디언 메뉴나 토글 기능 수정 시 `aria-expanded` 및 `aria-controls` 상태값을 자바스크립트에서 동적으로 업데이트해야 합니다.

### 2.4 시설 안내 매뉴얼 표(Table) 표준 모델
* **표준 모델**: `data/gagyeong_sportscenter_guide.md` (가경국민체육센터)를 시설 안내 매뉴얼의 표준 레이아웃으로 지정합니다.
* **지능형 셀 병합**: 동일한 열 내에서 상위 칸과 병합이 필요한 경우 마크다운 문법 내에 `^` 기호를 사용합니다. (예: `| ^ |`)
* **정렬 가이드**: 
    - 표의 제목(`th`)과 본문(`td`)은 원칙적으로 **왼쪽 정렬**(`text-align: left`)을 기본으로 하여 시각적 일관성을 유지합니다.
    - 단, 데이터의 성격상 중앙 정렬이 더 효과적인 경우에만 예외적으로 `:---:` 문법을 사용합니다.
* **이미지 갤러리**: 주요 시설 사진은 6장 구성을 표준으로 하며, `3x2` 그리드 레이아웃을 준수합니다.

### 2.5 콘텐츠 현대화 및 마이그레이션 지침 (Content Migration)
* **MD 변환 원칙**: `public/` 폴더 내의 레거시 HTML 매뉴얼은 가독성, 관리 효율성, 전역 검색 연동을 위해 반드시 마크다운(.md) 형식으로 변환하여 `data/` 폴더로 이관합니다.
* **데이터 통합 및 최적화**: 수십 개로 파편화된 HTML 파일(예: tech_manual)은 사용자 경험(UX)을 고려하여 연관된 주제별로 하나의 큰 MD 파일로 통합 관리하는 것을 권장합니다.
* **리소스 경로 수정**: 변환 시 이미지나 링크 경로는 현재의 표준 구조(`assets/`, `pages/` 등)에 맞게 최신화해야 합니다.

### 2.6 테스트 및 실험적 개발 지침 (Testing)
* **테스트 폴더 활용**: 새로운 기능의 실험, 임시 스크립트 작성, 시스템 구조 변경 테스트 등이 필요할 경우 반드시 최상위 루트의 **`test/` (또는 `scripts/test/`)** 폴더 내부에서 진행해야 합니다.
* **루트 청결 유지**: 최상위 루트 폴더에 임시 테스트 파일(`.js`, `.html` 등)을 직접 생성하는 것을 엄격히 금지합니다. 테스트가 완료된 후 운영에 반영할 때는 지침에 따라 정해진 폴더(`core/`, `assets/` 등)로 이동시키고 테스트 파일은 즉시 정리합니다.

### 2.7 파일 상단 표준 주석 지침 (Header Comment)
* **필수 기재 사항**: 모든 신규 파일 생성 또는 기존 파일 수정 시, 파일의 최상단에 해당 파일의 **파일명, 용도, 관리자 설명**을 한글 주석으로 반드시 기재해야 합니다.
* **작성 예시**: 
  ```javascript
  // 🚀 [파일명.js] 
  // 이 파일은 [기능 설명]을 수행합니다.
  // 관리자 안내: [조작 방법 및 주의사항]
  ```
* **특수 파일 대응**: JSON과 같이 표준 주석(`//`, `#`)을 지원하지 않는 파일 형식의 경우, `_comment` 또는 `description`과 같이 **시스템 작동에 영향을 주지 않는 가상의 필드(Field)를 생성하여 가짜 데이터 형식으로 설명을 추가**해야 합니다. (예: `"_comment": "..."`)

## 3. 업데이트 및 릴리스 노트 적용 프로세스
1. **백업 및 레거시 아카이브**: 수정 전 `versions/` 디렉터리에 백업본을 생성합니다. 또한 더 이상 사용하지 않는 레거시 파일(예: `.gitlab-ci.yml`, 구 버전 스크립트 등)은 즉시 삭제하지 않고 `_unclassified/archive/` 폴더로 이동하여 히스토리를 보존합니다.
2. **로컬 테스트**: 데스크탑 창 크기 및 모바일 해상도(크롬 개발자 도구)에서 레이아웃 깨짐이 없는지 확인합니다. 브라우저의 '뒤로가기' 버튼을 눌러 SPA 상태가 정상 복구되는지 검증합니다.
3. **업데이트 이력 관리 (릴리스 노트 작성)**: 작업이 완료되면 `docs/` 내에 현재 버전에 해당하는 폴더(예: `v5`)를 생성(또는 유지)하고, 그 안에 `버전_년월일.md` 포맷으로 당일 작업 내역을 요약한 릴리스 노트를 작성해야 합니다.
   * **작명 규칙 (Naming Convention)**: 현재 버전이 v5인 경우, 파일명은 `docs/v5/v5_260513.md` (예: 2026년 5월 13일) 형식으로 생성합니다. 향후 v6로 메이저 버전업 시 `docs/v6/v6_YYMMDD.md` 규칙을 따릅니다.
   * **필수 포함 내용**: 작업 일자, 주요 목표, 구조 변경 내역, 보안(시큐어 코딩) 준수 사항, UI/UX 버그 수정 내용 등.

## 4. 지침 준수 의무 (Compliance)
* 본 시스템의 모든 변경 사항은 `.cursorrules`, `1. SOS 프로젝트 시큐어 코딩 마스터 지침`, `2. 변경관리_및_UX개선_지침`에 명시된 규칙을 최우선적으로 준수해야 합니다.
* 모든 작업과 대화 시 해당 규칙들은 예외 없이 적용되며, 일관성 있는 시스템 유지를 위해 AI와 관리자 모두가 이를 철저히 따라야 합니다.
