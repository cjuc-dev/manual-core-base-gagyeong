# 🔄 변경관리 및 UX/UI 개선 지침

본 지침은 청주도시공사 'Smart Operations Suite (SOS)' 통합 매뉴얼의 뼈대(구조), 디자인(UI), 사용자 경험(UX) 등을 수정하거나 보완할 때 지켜야 할 표준 프로세스입니다.

## 1. 목적
* 무분별한 코드 수정을 방지하고 시스템의 안정성을 확보하기 위함.
* SPA(Single Page Application) 구조의 특성(상태 유지, 뒤로가기 등)을 훼손하지 않기 위함.
* 시큐어 코딩 및 웹 접근성 지침을 지속적으로 유지하기 위함.

## 2. UI/UX 보완 시 준수 사항

### 2.1 SPA 상태 관리 및 라우팅 (History API)
* **뒤로가기 지원**: 페이지를 이동(DOM 전환)할 때는 반드시 `history.pushState`를 사용하여 브라우저 히스토리에 상태를 기록해야 합니다.
* **이벤트 리스너**: 사용자가 브라우저의 '뒤로가기/앞으로가기' 버튼을 눌렀을 때 엉뚱한 페이지로 이탈하지 않도록 `window.addEventListener('popstate', ...)`를 통해 DOM 상태를 동기화해야 합니다.
* **닫기/명시적 이동**: 모달, 팝업, 문서 뷰어 등 화면을 덮는 요소가 열릴 때는 반드시 우측 상단이나 접근하기 쉬운 위치에 명확한 `[닫기]` 버튼을 배치해야 합니다.
* **상단 경로(Breadcrumb) 한글화**: 상단 네비게이션 경로 표시 시 영문 파일명(예: gym, program)이 아닌 **직관적인 한글 명칭(예: 다목적체육관, 프로그램실)**을 사용해야 합니다. 또한 카테고리에 따라 `문서: ` 또는 `시민의 소리 > `와 같은 명확한 접두사를 부여하여 현재 위치를 쉽게 파악하게 합니다.

### 2.2 스타일링 (Tailwind CSS & 전역 CSS)
* 인라인 스타일(`style="..."`)의 사용을 엄격히 금지합니다.
* **CSS 관리 및 스타일 분리 (CSS Management)**:
    - 전역 디자인(폰트, 카드 레이아웃 등)은 공통 CSS를 통해 일관성을 유지합니다.
    - **별도 스타일 적용**: 특정 마크다운(.md) 문서나 특정 섹션(예: VOC)에만 특수한 스타일을 적용해야 할 경우, 공통 스타일을 훼손하지 않고 **별도의 CSS 클래스(예: .voc-table, .voc-content)를 생성**하여 해당 영역에만 선택적으로 적용해야 합니다.
    - 하나의 스타일을 전체적으로 적용하여 다른 문서의 가독성을 해치는 행위를 엄격히 금지합니다.
* 다크/라이트 모드를 항상 고려해야 합니다. 특정 요소의 색상을 바꿀 때는 반드시 `dark:` 접두사를 포함한 다크모드 대응 색상도 함께 수정하십시오. (예: `bg-white dark:bg-gray-800`)

### 2.3 접근성 및 시맨틱 마크업
* 버튼 및 링크 추가 시 `aria-label`을 부여하여 스크린 리더기가 읽을 수 있게 하십시오.
* 아코디언 메뉴나 토글 기능 수정 시 `aria-expanded` 및 `aria-controls` 상태값을 자바스크립트에서 동적으로 업데이트해야 합니다.

### 2.4 시설 안내 매뉴얼 표(Table) 표준 모델
* **표준 모델**: `data/gagyeong_sportscenter_guide.md` (가경국민체육센터)를 시설 안내 매뉴얼의 표준 레이아웃으로 지정합니다.
* **지능형 셀 병합**: 동일한 열 내에서 상위 칸과 병합이 필요한 경우 마크다운 문법 내에 `^` 기호를 사용합니다. (예: `| ^ |`)
* **정렬 가이드**: 
    - 표의 제목(`th`)과 본문(`td`)은 원칙적으로 **왼쪽 정렬**(`text-align: left`)을 기본으로 하여 시각적 일관성을 유지합니다.
    - 단, 데이터의 성격상 중앙 정렬이 더 효과적인 경우에만 예외적으로 `:---:` 문법을 사용합니다.
* **이미지 갤러리**: 주요 시설 사진은 6장 구성을 표준으로 하며, `3x2` 그리드 레이아웃을 준수합니다.

### 2.5 콘텐츠 현대화 및 마이그레이션 지침 (Content Migration)
* **MD 변환 원칙**: `public/` 폴더 내의 레거시 HTML 매뉴얼은 가독성, 관리 효율성, 전역 검색 연동을 위해 반드시 마크다운(.md) 형식으로 변환하여 `data/` 폴더로 이관합니다.
* **데이터 통합 및 최적화**: 수십 개로 파편화된 HTML 파일(예: tech_manual)은 사용자 경험(UX)을 고려하여 연관된 주제별로 하나의 큰 MD 파일로 통합 관리하는 것을 권장합니다.
* **리소스 경로 수정**: 변환 시 이미지나 링크 경로는 현재의 표준 구조(`assets/`, `pages/` 등)에 맞게 최신화해야 합니다.

### 2.6 테스트 및 실험적 개발 지침 (Testing)
* **테스트 폴더 활용**: 새로운 기능의 실험, 임시 스크립트 작성, 시스템 구조 변경 테스트 등이 필요할 경우 반드시 최상위 루트의 **`test/` (또는 `scripts/test/`)** 폴더 내부에서 진행해야 합니다.
* **루트 청결 유지**: 최상위 루트 폴더에 임시 테스트 파일(`.js`, `.html` 등)을 직접 생성하는 것을 엄격히 금지합니다. 테스트가 완료된 후 운영에 반영할 때는 지침에 따라 정해진 폴더(`core/`, `assets/` 등)로 이동시키고 테스트 파일은 즉시 정리합니다.

### 2.7 파일 상단 표준 주석 지침 (Header Comment)
* **필수 기재 사항**: 모든 신규 파일 생성 또는 기존 파일 수정 시, 파일의 최상단에 해당 파일의 **파일명, 용도, 관리자 설명**을 한글 주석으로 반드시 기재해야 합니다.
* **작성 예시**: 
  ```javascript
  // 🚀 [파일명.js] 
  // 이 파일은 [기능 설명]을 수행합니다.
  // 관리자 안내: [조작 방법 및 주의사항]
  ```
* **특수 파일 대응**: JSON과 같이 표준 주석(`//`, `#`)을 지원하지 않는 파일 형식의 경우, `_comment` 또는 `description`과 같이 **시스템 작동에 영향을 주지 않는 가상의 필드(Field)를 생성하여 가짜 데이터 형식으로 설명을 추가**해야 합니다. (예: `"_comment": "..."`)

### 2.8 프리미엄 타이포그래피 표준 (Dinkus & Pullquote)
* **미니멀 딩쿠스(Dinkus) 도트 구분선**: 시설 안내 매뉴얼 내의 수평선 구분선(`<hr>`)은 세련되고 우아한 에메랄드/슬레이트 그레이 도트 `•   •   •` 딩쿠스 스타일로 렌더링해야 합니다.
    - **세부 비율 표준**: 도트 크기는 `16px` (`font-size: 16px`), 자간 간격은 콤팩트한 `0.6em` (`letter-spacing: 0.6em`), 오차 없는 정중앙 배치를 위해 `padding-left: 0.6em`을 고정 주입하여 정중앙에 단정하게 모인 콤팩트 비율을 유지합니다.
* **에디토리얼 풀쿼트(Pullquote) 인용구 카드**: 시민의 소리(VOC) 및 감성 정보전달 구역의 인용구(`blockquote`)는 연한 그라데이션 카드 배경과 좌상단/우하단의 대형 반투명 따옴표 기호(`“ ”`)를 조합하여 세련된 잡지 인용구 레이아웃으로 표현합니다. 

### 2.9 마크다운 최종 업데이트 일자 자동화 및 노이즈 소거 (Auto Date Injector)
* **버저닝 노이즈 제거**: 마크다운 파일 하단 푸터에 작성하던 `(Smart Operations Suite v5)`와 같은 불필요한 시스템 버전 표기는 중복 데이터이자 인지적 소음(Cognitive Noise)이므로 **엄격히 배제**하며, 간결한 `최종 업데이트: YYYY-MM-DD` 포맷만 표기합니다.
* **실시간 동적 날짜 자동 주입 (Auto-Update Date)**: 마크다운 파일을 수정 배포한 경우, 개발자나 관리자가 파일 내부의 날짜를 매번 수동으로 고치는 것은 인적 오류(Human Error)가 발생하기 쉽습니다. 
    - 따라서 시스템 로더(`index.html` 내 `loadContent`)가 서버 패치 시 반환되는 HTTP Response의 `Last-Modified` 헤더를 감지하여, 마크다운 내의 최종 업데이트 구문을 **실제 파일 수정 배포일(YYYY-MM-DD)로 동적 자동 치환**하도록 자동화 엔진을 탑재해 운영해야 합니다.

### 2.10 업데이트 히스토리 마스터로그 및 공식 문서 보안 은닉 표준
* **사용자 중심의 초슬림 요약**: 대면 히스토리 파일인 `data/update.md`는 기술적인 디테일(중첩 하위 리스트, 상세 픽셀 규격, 정규식 설계 사양, 기획 배경)을 철저히 배제하고, 사용자가 한눈에 변경 사항을 파악할 수 있는 **최상위 핵심 불릿(`- **기능명**`) 한 줄 형태**로만 요약 작성해야 합니다.
* **물리 경로 및 파일명 보안 은닉 (Information Disclosure 방지)**: 일반 대면 마스터로그에 영문 디렉터리 경로(예: `data/facilities/`, `data/system/`) 또는 시스템 전용 파일 규칙(예: `0. [foldername]_index.md`, `system_inquiry.md`)을 직접 노출하면 시스템 구조 유출 및 보안 취약점이 될 수 있습니다. 따라서 영문/물리적 경로는 마스터로그 상에서 전부 은닉하며, **한글 기반의 추상화된 비즈니스 서비스 용어로 대체 표현**해야 합니다. (예: '각 시설/폴더별 대표 목차 안내 체계', '매뉴얼 저장소 단일화', '문의 내역 파일 감지 시' 등)
* **리드미 및 공식 문서 내 로컬 물리 경로 노출 금지**: `README.md` 및 공식 시스템 설명서 등 사용자 대면/비공개 문서를 불문하고 **로컬 개발 환경의 absolute 물리 경로 및 로컬 파일 주소(예: `file:///d:/Smart%20Operations...`)의 기재를 엄격히 금지**합니다. 이는 로컬 디렉터리 정보 누출을 초래하는 보안 결함일 뿐만 아니라 협업 환경에서 링크 유실을 유발하므로 100% 영구 배제해야 합니다. 부득이하게 문서를 상호 참조할 경우 오직 리포지토리 기준의 상대 경로(예: `./core/markdown_parser.js`)만을 사용해야 합니다.
* **구현 디테일 및 괄호 노이즈 차단 (No Bracket Jargon)**: 업데이트 히스토리 작성 시, 괄호 `(...)`를 사용하여 구체적인 HTML 태그(예: `hr`, `blockquote`), 내부 기술 라이브러리/명칭(예: `marked.js`, `DOMPurify`, `Base64`), 스타일/개발 기법(예: `Tailwind CSS`, `SPA`, `카드형 UI`, `배지 연동`), 혹은 개별적인 세부 상태 텍스트(예: `접수중/처리중/완료`)를 직접 명시하는 행위는 **엄격히 금지하며 100% 영구 배제**합니다. 모든 내역은 오직 비즈니스적인 고차원 요약 형태로만 단정하게 서술해야 합니다.
* **앞으로의 버전 상승 및 스케일 제어 규칙 (Version Control Increment Rule)**:
    - 향후 배포 및 `data/update.md` 상의 버전은 **6.00**부터 시작합니다.
    - 무분별하고 과도한 버전 점프(예: v5.0에서 갑자기 v5.90으로의 대규모 점프)를 엄격히 제한하며, 주요 릴리스는 소수점 둘째 자리 단위(예: v6.00 ➔ v6.01 ➔ v6.02)의 체계적이고 안정적인 소규모 증분 방식을 따라 단계적으로 성장시켜야 합니다.
* **상세 내역은 개발 릴리스 노트로 위임**: 픽셀 값이나 정규표현식 등의 기술 설계 사양은 비공개 개발자 릴리스 노트(`docs/v5/v5_YYMMDD.md`)에 상세히 아카이빙합니다.

### 2.11 PC/모바일 기능 동등성 원칙 (Feature Parity Principle)
* **기능의 100% 동일 가용성 보장**: 데스크탑(PC) 버전에서 제공되는 모든 핵심 기능(예: 실시간 자동완성 추천, 상세 검색 본문 미리보기, 다단계 경로 네비게이션 등)은 모바일 환경에서도 단 1%의 누락이나 생략 없이 **완벽히 동일하게 구현 및 동기화**되어야 합니다.
* **사용자 경험(UX) 최적화와 기능 생략의 엄격한 구분**: 좁은 모바일 화면 및 터치 인터페이스 특성에 맞춰 레이아웃이나 여백(예: 자동완성 활성화 시 상세 결과창을 110px 수직 적층으로 밀어내어 공존시키는 기법 등)은 다르게 최적화할 수 있으나, **제공하는 데이터의 품질, 기능적 가용 범위, 상태 관리 로직 자체를 임의로 축소 또는 강제 은닉하는 행위는 엄격히 금지**합니다.
* **반응형 DRY(Don't Repeat Yourself) 구현**: PC와 모바일의 기능을 따로 작성하여 코드가 파편화되지 않도록, 하나의 반응형 함수 내에서 대상 컴포넌트(ID)만 지능적으로 감지해 스위칭 제어하도록 설계하여 결함 발생율을 최소화해야 합니다.

### 2.12 매뉴얼 이미지의 영문 서브디렉토리 고도화 구조화 및 로컬 완전 자립화 (Asset Localization & Path Standardization)
* **영문 폴더 표준 분류 규칙 (Directory Separation)**: 대량의 이미지 파일이 포함된 디렉토리(예: `manual/`) 관리 시, 파일 누락과 인코딩 이슈를 차단하고 가용성을 올리기 위해 이미지의 목적(예: 행정 매뉴얼 `admin`, 기술 매뉴얼 `tech`) 및 시설 영문명(`gagyeong` 등)을 따르는 영문 디렉토리 트리 구조를 엄격히 준수하여 아카이빙해야 합니다.
* **로컬 완전 오프라인 자립화 (100% Offline Parity)**: 외부 인터넷 및 원격 CDN망 연결이 완전히 단절된 인트라넷 또는 폐쇄망 내부 구동 환경에서도 매뉴얼이 정상적으로 구동되도록, 매뉴얼 내의 모든 외부 원격 URL 이미지 소스(예: GitLab 원격 주소 등)는 100% 로컬 영문 최적화 상대 경로(`../../../assets/images/manual/...`) 형태로 완전 전환하여 배포해야 합니다.
* **자동 마이그레이션 도구(Scripting) 활용 규정**: 대량의 정적 자산 경로를 수동으로 바꿀 때 유발되는 인적 휴먼 에러(경로 오타, 파일 누락)를 완벽 차단하기 위해, 경로 치환 작업 시에는 반드시 정밀 정규표현식이 탑재된 자동 마이그레이션 도구(`scripts/migrate_manual_assets.js` 등)를 로컬 Node.js 엔진으로 연동/작동하여 일괄 업데이트해야 합니다.

## 3. 폴더 구조 및 인덱스 관리 지침 (Folder Index Policy)

### 3.1 폴더별 인덱스 파일 의무화
* **규칙**: 모든 주요 디렉토리의 최상단에는 해당 폴더의 파일 구성을 설명하는 **`0. [foldername]_index.md`** 파일을 반드시 생성해야 합니다.
* **목적**: 관리자가 폴더 진입 시 파일별 용도와 수정 주의사항을 즉시 파악하여 관리 효율성을 극대화하기 위함입니다.
* **파일명 규칙**: 숫지 '0'을 접두사로 사용하여 항상 리스트 최상단에 노출되도록 합니다. (예: `0. core_index.md`)
* **필수 포함 내용**:
    - 폴더의 목적 및 역할 설명.
    - 주요 파일별 기능 정의 및 수정 가이드.
    - 파일 간의 상호작용 또는 의존성 정보.

### 3.2 신규 폴더 생성 절차
* 새로운 기능 구현을 위해 폴더를 생성할 경우, 해당 지침에 따라 즉시 인덱스 파일을 작성하여 구조를 명문화해야 합니다.

## 4. 업데이트 및 릴리스 노트 적용 프로세스
1. **백업 및 레거시 아카이브**: 수정 전 `versions/` 디렉터리에 백업본을 생성합니다. 또한 더 이상 사용하지 않는 레거시 파일(예: `.gitlab-ci.yml`, 구 버전 스크립트 등)은 즉시 삭제하지 않고 `_unclassified/archive/` 폴더로 이동하여 히스토리를 보존합니다.
2. **로컬 테스트**: 데스크탑 창 크기 및 모바일 해상도(크롬 개발자 도구)에서 레이아웃 깨짐이 없는지 확인합니다. 브라우저의 '뒤로가기' 버튼을 눌러 SPA 상태가 정상 복구되는지 검증합니다.
3. **릴리스 노트 작성**: 작업 완료 후 버전에 맞는 디렉터리(예: `docs/v6/`)에 `v6_YYMMDD.md` 형식으로 변경 사항을 상세 기록합니다.
   * **버전 명명 규칙 (Versioning)**: 대규모 개편 시 Major 버전을 올리고(v5, v6), 일반적인 기능 개선이나 수정 시에는 **v6.00부터 시작하는 소수점 둘째 자리 단위의 증분형 번호(v6.00, v6.01, v6.02...)**를 사용하여 누적 개선 횟수를 차근차근 점진적으로 관리합니다.
   * **필수 포함 내용**: 작업 일자, 주요 목표, 구조 변경 내역, 보안 준수 사항 등.
4. **통합 문서 동기화 (Mandatory Sync)**: 시스템 변경 시 아래 **3종 핵심 문서**를 반드시 동시에 최신화해야 합니다.
   * **`README.md`**: 프로젝트 개요 및 최신 디렉토리 구조.
   * **`docs/체육시설 통합 매뉴얼 시스템 설명서.md`**: 시스템 아키텍처 및 관리 가이드.
   * **`data/update.md`**: **릴리스 노트의 내용을 간소화/요약하여 히스토리 마스터 로그에 추가**.
5. **단축 명령어 운영**: 관리자가 **'업데이트'** 또는 **'업뎃'**이라고 요청할 경우, AI는 현재까지의 변경 사항을 분석하여 위의 **3종 핵심 문서**를 자동으로 최신화하고 보고해야 합니다.

## 5. 지침 준수 의무 (Compliance)
* 본 시스템의 모든 변경 사항은 `.cursorrules`, `1. SOS 프로젝트 시큐어 코딩 마스터 지침`, `2. 변경관리_및_UX개선_지침`에 명시된 규칙을 최우선적으로 준수해야 합니다.
* 모든 작업과 대화 시 해당 규칙들은 예외 없이 적용되며, 일관성 있는 시스템 유지를 위해 AI와 관리자 모두가 이를 철저히 따라야 합니다.
